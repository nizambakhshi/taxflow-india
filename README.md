# TaxFlow India

GST billing, invoicing and compliance for Indian businesses (₹2–20 crore) — cloud, no downloads, no per-seat pricing.

**Stack:** Next.js 16 (App Router, Turbopack) · React 19 · TypeScript · Supabase (Postgres + Auth, browser client) · Tailwind v4 tokens + a small custom design system in `src/app/globals.css`.

**Status:** Round 1 (7 competitive features), Round 2 through R2-37, and Round 3 through R3-9 (R3-1 — the append-only audit trail and financial period locks; R3-2 — the branch & document-series register and honest opening balances; R3-2b — the manual journal register, folded into the statements and guarded by the same seal; R3-4 — the filings register, the history of what each return stated and the paper that missed its window; R3-5 — the seal moved onto the writers, so every dated money path in the app asks the same door; R3-6 — the calendar learned the QRMP scheme and every date, sum and citation on it was re-read from a primary text; R3-7 — the deposit that scheme owes got its rupee, as a labelled ceiling until the shop names the cash tax; R3-8 — the Tally bridge reads journal and delivery-challan vouchers too, landing them as drafts on their own registers rather than skipping them; R3-9 — the books vault now remembers, book by book, what the last backup actually carried, so it can name what a browser wipe would take) are shipped — 65 pages and 54 pure domain libraries (67 route files: 65 pages plus the two `api/` handlers, and one more component file since R3-5 — 10 in `src/components`). Re-counted for R3-4: the sentence read "64 pages and 53 libraries (67 routes)", and on that day 64 + 2 was 66 — the parenthesis has only just caught up with the pages, which is why the arithmetic is printed with the number from here on. See `5-Project-Tasks.md` for the backlog, `1-PRD.md` for scope and `7-Competitor-Comparison.md` for where the product stands against Tally, Zoho Books, Vyapar, myBillBook, Busy, Marg, ClearTax and Refrens.

## Getting started

```bash
npm install
npm run dev          # http://localhost:3000
```

Environment (`.env.local`, never committed):

| Variable | Purpose |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Anon key used by the browser client |

Supabase schema and RLS policies are hand-managed in the Supabase dashboard — there are no migration files in this repo, and the working default is to ship a feature **client-side** (existing tables + `localStorage`) rather than change the schema. See `3-Development-Rules.md` Rule 21.

Checks before committing:

```bash
npx tsc --noEmit
npm run build
npx eslint <files you touched>   # `next lint --file` no longer exists in this Next build
```

Pure libraries under `src/lib` are tested with a TypeScript loader, not a test runner:

```bash
node --experimental-strip-types --no-warnings --import /tmp/jr-register.mjs /tmp/<lib>-test.mjs
```

(`jr-register.mjs` registers the `resolve()` hook that maps `@/lib/…` onto `src/lib/…`; the suites themselves live in `/tmp` and are not committed, which is why each round records its own assertion counts in `5-Project-Tasks.md`.)

## What the app does

**Day-to-day:** business setup, customers, vendors, products, sales invoices (B2B/B2C/Export/SEZ), purchase bills, expenses, payments, quotations, credit/debit notes, delivery challans with the Rule 55 reason handling, sales and purchase orders that convert into a real invoice or a real bill, inventory with stock movements, batch/expiry lots drawn FEFO by the invoice itself, one-row-per-unit serial numbers with warranty derived from the latest sale, a godown register where a transfer is a lot split, a recipe book where a recipe stores quantities and minutes — parts priced from the product master, the time priced from dated shop-rate rows in force on each run's own day, with a dash and a reason where a rate is missing — and a build draws them from named lots — FEFO proposed, overrulable by hand — through the same stock RPC, lands the finished units as their own lot, gives the units back to the lots they came from when the run is cancelled, and — since R2-35 — lets a serialled component's draw name the actual numbered units: the oldest on the shelf proposed first, overrulable chip by chip, the register refusing a pick set that does not cover the drawn quantity to the unit, each pick issued as the register's own event with its job number, and a cancel writing each unit back on the shelf with an event of its own, with a demand tab that names the component stopping today's run, recurring invoice schedules that bill into the financial year they belonged to, foreign-currency deals kept beside the rupee books, settings.

**GST:** dashboard, GSTR-1 and GSTR-3B workpapers, GSTR-2B ↔ books reconciliation, e-invoice (IRN) + e-way bill payloads, GSTR-9/9C annual workpaper, GSTR-4/CMP-08 composition workpaper, job-work register with the section 143 return clock and the four ITC-04 grids, an export register that runs both clocks on every consignment that left India — the letter of undertaking that keeps the supply zero-rated and the FEMA window the proceeds have to arrive inside, with the refund limitation and the advance-dispatch deadline beside them and the source disagreement left visible rather than resolved silently, compliance calendar with late-fee estimates (it reads the export watch list from the register instead of keeping its own dates), statutory registers (party-wise, HSN/SAC, B2B, state-wise, e-way bill, order flow).

**Money:** party ledger & statements of account, P&L and balance sheet derived from documents, cost centres and departments that split an invoice, bill or expense by share — the percentage is what is stored, the rupees are re-read from the documents on every load, so amending a bill re-splits every centre by itself, projects & time — hours logged against a job with the whole invoices and bills that belong to it attached by id, rupees re-read from the books on every load so nothing here can rot, unbilled months priced and watched against the 30-day invoice window rule 47 asks for (a date, a rule and a link — never a tax figure), "billed" recorded as a reference to paper raised elsewhere rather than a document this page creates, and — since R2-36 — an hour that names whose hours they were: the person is picked from the payroll register, the hour is costed at what their hour cost in exactly the entry's own month (the rows cross as data; the projects library imports no payroll code), and the reading prints "after named hours" beside contribution — marked partial while hours remain unnamed or unpriced, never folded in, and — since R2-37 — a timesheet that draws from the kept day book: a person-month of marks arrives as proposed rows (a present day at the register's own hours a day, half a mark as half, every other mark refused with the register's own sentence, a day already on the project un-tickable), and only your tick writes — through the same entry validator the manual form uses, with the drawn row naming the person so it is costed the moment it lands, receivables/payables ageing, bank statement matching (any bank's layout, scored against open documents with the reasons shown), TDS & 194Q withholding workpaper read out of the purchase bills with deposit calendar and interest, UPI payment links and WhatsApp reminders, a dated FX rate ledger with realised and unrealised exposure beside the rupee books, targets with festival-weighted pacing, demand-driven reorder suggestions, a payroll & salary register that stores each person's pay structure and their exceptions but keeps no rupee — every month re-walks the financial year for its own take-home (section-192 annualisation, the PF wage ceiling read by the month's last day so ₹15,000 becomes ₹25,000 on 17-09-2026, the ESI band, professional tax capped at ₹2,500 with a dash and a reason wherever a state's rate is not verifiable), takes the shop's own attendance sheet as a paste rather than a table — a summary column or a day grid, read for one figure only, with every match, every refused line and every person the sheet forgot printed for approval before a month row is touched — and, since R2-34, **keeps the days** in a day book on the same page: the month ruled with dates, one mark per person per day tapped or pasted, held as evidence that carries no rupee until the shop pulls it into the month through the month form's own validation, with a blank day counted nowhere and a page refused by the *kind* of the line that could not be placed rather than by the wording of its reason — and prints what an hour actually cost on its own Cost tab — a figure `/projects` now reads as a costed hour whenever a timesheet row names the person it belongs to, printed beside contribution rather than folded into it. That register now also ends as **paper**: `/payroll/payslip` lays one person's month, or the whole month, out as an A4 slip whose every rupee is laid out from the engine's own reading, so a slip cannot disagree with the screen it came from — *net payable* rather than paid, a dash and a named sentence beside a letterhead code nobody typed, no figures at all for a month the register refuses, the exceptions printed in a strip on this side of the paper, and one PDF of a sheet per person for the month.

**In control (R3-1):** `/audit` is an append-only register of the decisions a shop makes about its closed periods — every period sealed, every seal released, every write a seal stopped, and every note lands as a numbered event, and the page can honestly say the trail is *unbroken* because the `seq` numbers run 1..n with no gap, duplicate or reorder (a checksum over the trail, not a signature — it proves a hand-edit happened, it cannot name the keyboard that did it). A **period seal** closes a GST period that has fully ended, and a document dated inside a standing seal is refused at the door that asks it: the seal shipped in R3-1 with exactly one door — `/invoices/new`, the moment the invoice date lands in a sealed month a red lock banner appears under the field, the save is refused with the seal's own sentence, and the attempt is written back to the register as a *Write refused* event, so the edit that never happened is still on the record. That first round printed the rest of the paths as open by name rather than implying them; **R3-5 closed them**, and which paths are covered, and where each one asks, is now a counted list on the seals tab rather than a sentence in prose (see *At every door* below). Releasing a seal keeps it (released, never deleted) and demands a reason, because a silent unlock is exactly what an auditor looks for. The register holds no rupee, lives in this browser (ADR-013), travels only inside the books vault, and files nothing to the portal.

**At the desk (R3-2):** `/business` answers *where* the shop issues from and *what its numbers wear* — and nothing else. A **branch** is a full registration: its own 15-character GSTIN and the state code that GSTIN starts with, refused as a pair when they disagree, because place of supply and the CGST/SGST split read that pair. The invoice form offers an *Issuing branch* that swaps the printed header and stamps the notes with `[branch CODE]`; the print page reads the stamp back, and a branch deleted after its papers leaves the page naming a fallback rather than silently substituting. Deleting a branch whose name is still stamped on documents is refused — history does not go out of business; deactivate it instead — and the head office cannot close or vanish until the head is handed over. A **document series** dresses the five kinds this app numbers (tax invoice, quotation, delivery challan, sales and purchase orders): prefix up to eight characters, count padded 1–8 digits wide, the financial year optionally inside the number — and *only the shape is the shop's*. The counters stayed where they were (the Supabase `invoice_sequences` row for invoices; each order register's own high-water walk for the rest, which reads every shape a kind has worn, so nothing gets numbered twice and an untouched shop sees no change at all). Change a shape mid-year and papers already issued keep the shape they were born with. Two series with one prefix are refused — they would issue the same number twice. This register holds no rupee: the **opening balances** it replaces live on the Financial statements page, which since this round grows bank, receivable and payable lines and an *as-of* day the books were picked up — a balance sheet drawn before that day shows the documents it has, not an opening it was not yet standing on, and a payment grows cash without pretending to reduce an opening receivable it cannot name. The primary registration in Settings still signs the statutory pages (GSTR-1, e-invoicing); a branch here is what your paper prints. The register lives in this browser (ADR-013) at `taxflow:setup:<orgId>` and travels inside the books vault.

**By hand (R3-2b):** `/journal` is where a rupee that is real, lawful and has no paper behind it gets a name. Everything else here is written *backwards* from a document — an invoice makes revenue, a bill makes a payable, a payment moves cash — and a journal entry is written *forwards*: depreciation is ₹40,000 this year, the loan arrived but no bill did, the owner took money out of the till, a GST notice has raised a liability no bill carries. A **head** is the shop's own word for a line of the statements and it declares which of the fifteen lines its rupee moves — that declaration is the only place the debit/credit convention lives, so a fold cannot get an income leg backwards; an **entry** is at least two legs; and nothing reaches a statement that has not been **posted**, which is only allowed when the two sides agree to the paisa (every sum in the register runs in paise, so a float tail cannot decide whether an entry balances). A head cannot be debited and credited in the same entry; a closed head is not offered a new rupee; a leg of ₹0 says nothing. A posted entry is **reversed, never edited or deleted** — the mirror re-summonses each leg from the original with its side flipped, so a correction cannot drift from what it answers, both halves stay on the register, and the pair nets to nothing while remaining visible. And because every posting balanced on the way in, an entry **renames money and provably cannot move the derived "Capital account (derived)" plug** — that arithmetic is read off the rows the sheet is actually holding and printed beside the figures (`/accounting` names it, `/ai/ask` prints the same caveat rather than folding judgement into document totals). Numbers wear `/business`'s sixth series shape and are counted by this register alone; a draft takes no number, so deleting one cannot punch a hole in a series an auditor reads. **The seal is the second door here**: an entry dated inside a standing period seal is refused before its legs are even read, and the *attempt* lands on the audit trail. It files nothing — no return reads a journal row — it settles no bill, and it does not reach the bank; there is no chart of accounts, no account codes and no trial balance, only the shop's own named movements beside the derived paper. The register lives in this browser (ADR-013) at `taxflow:journal:<orgId>` and travels inside the books vault.

**What it told them (R3-4):** `/gst/filings` answers the two questions a department asks and this app had no page for — *when did each period's return actually go in, was it late, what did it state*, and *what did you do about the invoice you missed*. The calendar only knows a return is due and carries a tick; `/gst/gstr9` only knows what a year's 3B stated for 9C. A **row is a transcript, not a posting**: the figures on it are what the return *stated*, nothing here is read by `ledger.ts`, and the `reference` is stored exactly as the shop writes it because this register never checks it against the portal. Each row snapshots the due date the app's calendar stated and then **audits it** — `statutoryDue()` re-derives the date from the rule (20th under rule 61(1)(i); the 22nd or 24th under 61(1)(ii) by the state of your principal place of business; 18th under rule 62(1)(i); 30 June under the proviso to 62(1)(ii) from FY 2024-25) and prints any place the two disagree. (Until R3-6 this also had to *fold* a QRMP filer's twelve monthly calendar rows into the four quarters the rule names; R3-6 fixed the emitter itself, so the fold that remains is only of a period **key** — a row saved against any month of a quarter still lands in the quarter that owns it.) Late fee runs on **the slab that applies, not the headline** — ₹50 a day under section 47, but the ceiling is ₹2,000 / ₹5,000 / ₹10,000 by the preceding year's turnover under Notifications 19, 20 and 21/2021-Central Tax (₹500 on a nil return), and GSTR-9 has its own three slabs capped at 0.04% or 0.50% of the turnover *in that State or Union territory* under Notification 07/2023 — and the line prints which notification decided the number, beside the calendar's ₹5,000 reading rather than merged into it. An **amendment is dated against the window that still allows it**: the proviso to rule 59(1) (open after that period's GSTR-1, shut the moment its 3B goes in), Table 9A of the annual return, and section 16(4)'s credit deadline — 30 November following the year, or the annual return, whichever came first, per Circular 237/31/2024-GST — so a correction nobody can file any more prints as **lapsed** instead of sitting on a to-do list forever. The register also reads the chain the rules already enforce: rule 59(6)(a) will not take a GSTR-1 while the previous period's 3B is unfurnished, 59(6)(b) names the Invoice Furnishing Facility for a quarterly filer, and 59(6)(d) stops the next GSTR-1 while a rule 88C(1) intimation stands unpaid — the bar is printed on the row with the citation and a link to the row that has to go in first. A third tab compares what each filed return **stated** against what the books hold, head by head, within ₹1; a nil row is compared as nothing, and an unfiled period is not compared at all. It wears R3-1's seal honestly: the badge on a row is *read* from the audit trail, "seal this period" hands the work to `/audit` and keeps its rules (a running month and an overlapping year are both refused, and a quarter is refused by naming its three months), every status change writes one line to that same trail, and — unlike the journal — a filing record moves no rupee, so no door asks this register's permission. Three CSVs (the grid at 27 columns, the board at 17, the variance at 10), five named things it does not track — the portal itself, the IFF, PMT-06, refunds and DRC notices, and any effect on the statements — and the same life as every other register: this browser at `taxflow:filings:<orgId>`, the thirty-fifth spec in the books vault, ⌘K, and its own glyph (`filing`, a filed return with the portal's tick on it).

**At every door (R3-5):** R3-1 shipped the seal with one door — the invoice form, which asked for itself. This round moved the door off the pages and onto the code that writes: `createInvoice`, `createPurchaseBill` and `createNote` each call `requireOpenSeal` as their *first* statement, before a sequence number is spent, so a save dated inside a standing seal is refused and **no number is burned by a refusal**. Everything that saves through those three inherits the door without mentioning a seal — `/pos`, the `/recurring` catch-up run, the `/offline` outbox replay, `/sales-orders` and `/purchase-orders` converting, a challan becoming an invoice, the `/tally` import, a scanned bill, `/bills`, `/credit-notes`, `/debit-notes` — and each of them prints the seal's own sentence where it prints any other failure (the counter's form error, the run's error line, the order page's alert, the Tally plan's per-row "why"). The rest type straight into their table, so those pages carry the door themselves: `/expenses`, `/payments` (the payment date — a lock on the till, not on the books), the paid and cancel stamps on `/invoices` and `/bills`, a `/quotations` conversion, and the scanned-receipt half of `/ai/scan-bill`. `/journal`'s door is inside `journal.ts`, asked before its legs are even read. `/audit` now prints the whole list with the hand written on each row — **19 of 21 paths consult the seal, 12 of them inside the shared writers** — and the two it leaves open are printed as open rather than quietly dropped: a master record carries no date and moves no rupee on a statement, and a return's filing status is a transcript, which *reads* the seal and is never stopped by it. Beside every date field that could break a window sits one component, `SealNotice`, which draws the red banner under the field before Save is pressed and deliberately only *reads* (`sealGuard`) — a banner appearing on screen is not an attempt to write, and an attempt is the only thing that belongs on the trail; the refusal itself is logged by the same handler as a *Write refused* event. A seal is a statement about a window from the moment it stands: it never rewrites or erases paper already issued, and nothing in this round needs a new register — no new `localStorage` key, so the vault is unchanged at 35 specs. What it cannot do is named the same way: the door is in this app's writers, so a row changed outside them — the Supabase table itself, another client — is not stopped, exactly as the trail is a checksum over `seq` and not a signature.

**On the calendar (R3-6):** a QRMP filer's calendar used to print twelve monthly summary rows and say, in a footnote, that the shop actually files four quarters. The footnote was the app admitting its own screen was wrong. This round the emitter learned the scheme: `generateEvents()` prints the **four** GSTR-1 and GSTR-3B quarters rule 61(1)(ii) speaks of, plus the paper and money a quarter leaves behind — **eight** Invoice Furnishing Facility windows on the thirteenth (the day rule 59(2) fixes in its own words) and **eight** FORM GST PMT-06 deposits on the twenty-fifth (rule 61(3)). Which of the two quarterly days applies is a fact about the shop's principal place of business, so the calendar now has a state control and `qrmpCategory()` is the **one** function that places a shop in the rule's two rows — `src/lib/filings.ts` deleted its own half-read copy of that table and re-exports the emitter's, because the code that sets a date and the register that audits it must not be able to disagree. The round's second half was a **citation sweep** against primary texts (CBIC's own rule 61 / rule 59 pages, the Council's Notification 83/2020 and 85/2020 PDFs, Circular 143's own PDF), and it removed six things this app had been printing as authority: a "six per cent" deposit figure, a pair of notifications dated 17.02.2025 that do not exist under those numbers, a Circular dated 23.02.2020 with a reading that appears nowhere in it, a 12% interest cap under "the second proviso to rule 61(3)" (no such proviso exists), a claim that rule 61(4) bars a top-up, and the 35% deposit amount attributed to a Circular paragraph when it is **notified law** — Notification No. 85/2020-Central Tax dated 10.11.2020, under section 148 read with the proviso to section 39(7). Where a date comes from an instrument the register has not read, `statutoryDue()` now returns `cited: false` and a citation that refuses to name one. An unnamed state gets the **earlier** of the two days and the register reports those periods as *cannot be checked*, rather than confirming a date it guessed.

**The deposit gets its rupee (R3-7):** rule 61(3) fixes the twenty-fifth and states **no amount**, so those eight deposit rows printed a day and an empty rupee. The notified sum is thirty-five per cent of the tax paid **in cash** in the return for the immediately preceding quarter, and this app keeps what a return *stated in total* — not which ledger it left from — so `depositFor()` folds the base quarter's own filed GSTR-3B row into a **ceiling**, printed as *up to ₹…* in amber with the line it was read from, and the shop's own cash figure turns it into a **ready** challan. The number the shop states is stored as `cash:<quarter>` inside the envelope the calendar already owns, so no new key was created and the vault's compliance row now counts its two kinds of entry apart — *2 returns marked filed · 1 quarter with a stated cash tax*. Nothing here reads the electronic cash ledger or the portal: the card says *state*, never *this is what you owe*, and the challan on the GST site stays the record.

**The vault knows which books moved (R3-9):** a backup used to answer *when did you last take a file, and how big was it* — which is not the question a wiped browser makes urgent. Each recorded backup now also leaves a **fingerprint per register** in the vault's own log: the rows counted that day and the *same* FNV-1a checksum the file's block was packed with. The Registers tab reads this browser against that memory and answers *which books moved since your last file* — in your file, changed since, new since, only in your file, empty, cannot tell, in no file yet. The answer comes from **content compared to content**, never from a timestamp, and never from the file: that copy is in a folder or a mail and this screen cannot know what it became after it left. The fingerprints therefore stay on the device — they ride the log key that is deliberately never inside a vault file, so a second laptop restoring the same backup inherits the books, not the claim, and no new `localStorage` key was created (Rule 31 stayed untriggered, the vault is still 35 specs / 30 restorable). The two states that admit ignorance are printed rather than smoothed: a backup taken before this browser kept fingerprints says **cannot tell** instead of guessing, and a hand-edited log is sanitised on the way in, so an invented checksum can still only ever *compare* — it reads *changed*, never *in your file*. What the shop gets is **"What a wipe would take with it"**: the books with content newer than any file it has taken, each with a link to the page that owns it and a button that takes a backup now — and a book the file carries but the browser no longer does is *not* on that list, because there the file is the copy that survives.

**At the counter and on the move:** POS screen with camera barcode scanning, installable PWA shell with an offline invoice outbox that replays through the normal save path, ⌘K command palette over pages, actions and live records, and customer statements that travel inside their own share link — the whole statement is encoded in the URL fragment, so nothing is stored server-side and there is nothing to revoke.

**Moving between books:** `/tally` reads a Tally .xml export in the browser and shows a plan — every voucher mapped to an invoice, bill, credit/debit note, or (since R3-8) a journal or challan **draft** on its own register, against the document and master names it already holds, each line matched to a product and party, with blocked documents named and reasons printed before a single row is written. Export goes the other way: a proper Tally XML envelope built from real invoices, labelled with what it contains and what it doesn't. Nothing leaves the device; the import log tells you exactly what ran and when.

**AI-ish, deliberately offline:** supplier bill scan (OCR/PDF → structured line items, cross-checked against GST arithmetic) and natural-language reporting over the user's own books. Both run entirely in the browser — no bill is uploaded anywhere, and every figure traces back to the rows it came from.
